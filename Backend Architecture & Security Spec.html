01Executive summary

The Operator Console today is a high-fidelity front-end prototype. Authentication, scoring, and the content pipeline all run in the browser, which is perfect for demonstration but provides no real security and no shared, durable state. This document specifies the backend that turns it into a real product.

The chosen shape is serverless and Azure-native: a static front end on Azure Static Web Apps, a Python FastAPI service running on Azure Functions, and a managed PostgreSQL database. Secrets live in Azure Key Vault and are reached through a managed identity, never shipped to the browser. The blog-automation pipeline runs as queue-driven and timer-driven Functions so long jobs never block a request. Every external call (WordPress, Google Search Console, Groq, Azure OpenAI, email) moves server-side.

The security program follows the OWASP Top 10 and OWASP ASVS as its checklist, and Section 12 audits the current prototype line by line so nothing carries forward silently.

02Goals & non-goals

Goals

  • Server-enforced authentication and authorization; the UI gate is never the security boundary.
  • One durable source of truth for posts, pipeline state, leads, media, and rankings.
  • All API keys and credentials held server-side in Key Vault; zero secrets in client code.
  • The automation chain (discover, draft, humanize, SEO, image, review, publish) runs reliably with retries and a full audit trail.
  • Stays inside Azure free / 12-month-free allowances at portfolio traffic, with a clear paid scaling path.
  • Defensible against the OWASP Top 10 and compliant with PIPEDA and GDPR for site visitors.

Non-goals (v1)

  • Multi-tenant SaaS. This is a single-operator console for one site owner plus a small number of roles.
  • Replacing WordPress as the published-content host. WordPress stays; the backend orchestrates it over REST.
  • Real-time collaboration or websockets. The console is single-author and poll/refresh is sufficient.

07Authentication & session security

This section replaces the prototype's browser gate with a real, server-enforced scheme.

Passwords

Hashed with Argon2id (memory-hard, tuned cost), unique salt per user, never logged. Minimum length 12, checked against a breached-password list. No password is ever returned by any endpoint.

Sessions & tokens

On login the server issues a short-lived access JWT (about 15 minutes) and a long-lived refresh token, both delivered as HttpOnly; Secure; SameSite=Strict cookies so JavaScript cannot read them. The refresh token is stored only as a hash in sessions and is rotated on every use; reuse of an old token revokes the whole family (theft detection). Logout and "sign out everywhere" revoke server-side.

OTP password reset

Reset generates a 6-digit code, stores only its hash with a 10-minute expiry and a 5-attempt cap, and emails it server-side (Section 9). Codes are single-use and rate-limited per account and per IP. Requesting a reset never reveals whether an email exists.

Defense in depth

  • MFA (TOTP) available for the owner role; secret encrypted at rest.
  • Rate limiting + lockout: progressive backoff on failed logins, temporary lock after repeated failures.
  • CSRF: double-submit token on all cookie-authenticated mutations, plus SameSite=Strict.
  • Audit: every login, logout, reset, role change, and publish is written to audit_log with actor and IP.
Migration note

The prototype's default credentials and demo banner are removed in production. The first owner account is created by a one-time seeded invite, then forced through a password set on first login.

08Automation pipeline backend

The pipeline (discover, plan, draft, humanize, SEO, image prompt, review, publish) becomes a chain of small workers instead of one long request. An API call only enqueues work; Functions do the rest.

Queue
Each stage drops a message for the next on success; Azure Queue Storage decouples producers from workers.
Scheduling
A Timer Function runs daily discovery; a poller advances eligible jobs.
Idempotency
Each job has a stable key; re-delivery is safe and never double-publishes.
Retries
Exponential backoff with a max attempt count; exhausted jobs land in a dead-letter state surfaced in the UI.
Human gate
The review stage blocks on operator approval; nothing reaches WordPress without it.
Observability
Every transition writes pipeline_jobs.state and an App Insights event for tracing.
Cost guard

AI calls (Groq, Azure OpenAI) are the only metered step. The worker enforces a per-day token budget and short-circuits when exceeded, so a runaway loop cannot generate a surprise bill.

09Integrations & secrets

Every third-party credential lives in Key Vault and is read at runtime through the Function's managed identity. None are in the repo, in environment files committed to source, or in client code.

The current OTP demo uses an EmailJS public key embedded in the browser, which anyone can read and abuse. In production the browser never sees an email credential; all sending is server-side through Azure Communication Services or authenticated SMTP.

10Contact form & lead inbox

The public form posts to POST /public/contact, the only unauthenticated write in the system, so it is the most defended.

  • Validation: Pydantic checks field shapes and lengths; the body is treated as untrusted text and stored escaped.
  • Spam control: a hidden honeypot field, a minimum fill-time check, per-IP rate limiting, and an optional Cloudflare Turnstile / hCaptcha challenge. A computed spam_score auto-files likely junk.
  • Storage: rows land in leads; the operator triages them in the existing Query Inbox UI.
  • Notification: a new genuine lead emails the owner; replies are sent from the server, never exposing the inbox address in markup.
  • Privacy: IP is stored only for abuse handling and purged on a retention timer (Section 13).

13Privacy & compliance

The site collects personal data through the contact form and stores operator accounts, so it falls under Canada's PIPEDA and, for any EU visitors, the GDPR.

  • Data inventory: leads (name, email, message, IP), user accounts, audit logs. Nothing sensitive beyond contact details.
  • Lawful basis & consent: a plain-language notice on the form; no pre-ticked boxes; analytics only with consent.
  • Retention: lead IPs purged after 30 days; closed leads archived then deleted on a schedule; audit logs kept 12 months.
  • Rights: a documented path to export or delete a person's data on request (DSAR), satisfied by simple queries on leads.
  • Minimization: only fields the form needs; no third-party trackers by default.

16Implementation roadmap

1Foundation~ week 1

Bicep for the resource group, Static Web Apps, Functions, Postgres, Key Vault. CI/CD with OIDC. Empty FastAPI app deploying green.

2Auth & data~ week 2

Schema + Alembic. Argon2 login, rotating sessions, OTP reset, MFA, rate limiting, audit log. Wire the existing UI gate to the real API.

3Core console API~ weeks 3–4

Posts, pipeline board, media, rankings, server-side SEO scoring, lead inbox. Replace the prototype's static data with live endpoints.

4Pipeline & integrations~ weeks 5–6

Queue/timer workers; WordPress publish; GSC sync; Groq/Azure OpenAI with token budget; ACS email. Public contact form with spam defense.

5Harden & launch~ week 7

Headers/CSP, dependency scan, pen-test pass against the OWASP checklist, monitoring + alerts, backup/restore drill, privacy notice. Production swap.

Where this leaves you

This spec is buildable as written and stays free at your scale while showcasing exactly the Azure architecture skills your certifications cover. The single most important change is Section 7: until authentication is enforced on the server, the console is a demo, not a protected system.
